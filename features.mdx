## Travel Data Sync

TourData Mirror synchronizes travel data from upstream systems into a local mirror for reporting and API access. The mirror stores trip, booking, and disposition data so downstream applications can query a consistent local representation.

Two sync schedules keep the mirror current:

- **Nightly full sync:** Refreshes the complete trip, booking, and disposition catalog overnight.
- **Frequent imminent-trip sync:** Refreshes trips departing within 7 days and currently running trips every 30 minutes during business hours in the development environment.

<Callout kind="info">

Frequent trip sync is currently enabled in the development environment only.

</Callout>

Disposition-to-trip linking uses three levels of precedence:

1. Use the planned trip returned by the upstream API.
2. If more than 50% of dossiers share a trip, use the majority-dossier match.
3. If neither match is available, use an exact title or code match.

The mirror stores planned and booked trip views separately. This distinction preserves the upstream plan while allowing reporting to reflect the trip associated with each booking.

## Aggregate Analytics

The aggregate API provides queryable datasets for operational reporting across vehicles, staff, departures, bookings, and feedback.

| Dataset | Measures | Key dimensions |
| --- | --- | --- |
| `vehicle_days` | `full_days`, `half_days`, `operating_days` | `day`, `week`, `month`, `year`, `brand`, `trip` |
| `staff_days` | Staff counts | `day`, `week`, `month`, `year`, `role`, `category`, `vehicle` |
| `departures` | `departures`, `pax` | `day`, `week`, `month`, `year`, `brand`, `trip`, `country` |
| `bookings` | `bookings`, `pax` | `day`, `week`, `month`, `year`, `brand`, `trip`, `status` |
| `feedback` | `avg_rating`, `NPS` | `day`, `week`, `month`, `year`, `brand`, `trip`, `question` |

### Query behavior and limits

- `vehicle_days` queries with the `day` dimension support up to 366 days.
- Other datasets support a maximum range of 92 days.
- Bookings queries without a status filter return non-cancelled bookings by default.
- Aggregate responses include human-readable labels for brands, trips, countries, categories, and questions.
- Destination country values use ISO 3166-1 alpha-2 codes.
- The values endpoint accepts optional date bounds. When omitted, it defaults to a one-year window.

<Callout kind="tip">

Use `format="analytics"` when a result feeds a chart. Typed columns and units let visualization clients render measures without inferring their meaning from raw values.

</Callout>

## Dossier Generation

KD Dossier generates travel documents and PDF exports from mirrored booking and trip data. Exported documents use the same state that editors see, including changes made at both travel and departure levels.

### Export workflow

<Steps>
  <Step title="Use the editor state" icon="edit">

  The export inherits the current document state from the editor, including travel-level and departure-level changes.

  </Step>
  <Step title="Refresh saved dossier data" icon="refresh-cw">

  Saved dossiers refresh with current booking data before export so the generated document reflects the latest mirrored information.

  </Step>
  <Step title="Resolve departure locations" icon="map-pin">

  Each booking uses its own boarding location instead of the trip's first departure point. Arrival text also references the booked departure location.

  </Step>
  <Step title="Generate the export" icon="file-text">

  The system validates the request and produces the travel document or PDF using the resolved data.

  </Step>
</Steps>

### Export validation

Cross-tenant exports return HTTP 403 instead of generating a document with the wrong brand. Invalid requests return meaningful error messages rather than an empty PDF or a generic HTTP 503 response.

### Editor capabilities

Deleted sections can be restored after reloading, and the restored sections return to their original position. Block actions target blocks by stable key, preventing edits from applying to the wrong block when hidden or grouped blocks change their visible position.

## Shared Platform

The fullstack starter provides shared infrastructure for TWG applications. These components keep common identity, navigation, notes, and API behavior consistent across products.

| Component | Purpose |
| --- | --- |
| Entity Notes | Attach notes to bookings, trips, and customers, with notes shared across applications. |
| App Switcher | Navigate across applications using environment-aware URLs. |
| User Menu | Display the current identity and provide logout behavior. |
| Entra ID Auth | Renew sessions silently and recover automatically from expired tokens. |
| Versioned API | Expose domain endpoints under `/api/v1/` while reserving `/api/v2/` for future changes. |

<Callout kind="alert">

Existing integrations that use `/api/...` must update their requests to `/api/v1/...`. The versioned path is a breaking API change.

</Callout>
