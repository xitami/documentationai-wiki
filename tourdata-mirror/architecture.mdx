## Architektur-Übersicht

The TourData Mirror is built as a Python/FastAPI application with a clear separation between upstream data ingestion, local storage, and read APIs. The primary runtime is `src/tourdata_mirror/api/main.py`, which mounts all business routers under `/api/v1` with health probes at `/health` and `/ready`.

```mermaid

    A[Web Trip API] --> E[tourdata_client.py]

    K --> K5[kd-doc]
    K --> K6[Notes]
    K --> K7[Mail]
    K --> K8[Alerts]
    K --> K9[Events]
```

The upstream APIs remain external systems. `tourdata_client.py` handles their HTTP authentication, retries, pagination, and client-specific requests. Synchronization modules transform those responses into local PostgreSQL records using initial backfills and incremental ingestion.

FastAPI and the MCP server consume the local database representation rather than querying the upstream systems for every request. CLI tools and the nightly Azure Function invoke the same synchronization modules, which keeps operational and scheduled ingestion paths aligned.

### Runtime boundaries

The API application is the primary runtime boundary. `api/main.py` mounts business routers under `/api/v1`, while `/health` provides a liveness probe and `/ready` verifies database readiness with a database query.

The synchronization boundary is separate from the request-serving boundary. Modules under `sync/` manage trip, booking, customer, survey, personnel, and disposition ingestion. They track synchronization runs, cursors, statuses, record counts, timestamps, and errors in the `_sync` schema.

Configuration is centralized in `config.py`. It resolves environment settings, tenant-specific TourData credentials, authentication settings, and domain-specific feature flags used by the API and background operations.

## Datenbank/API-Trennung

<Callout kind="info">

Upstream systems are remote and relatively slow. The mirror stores a local, queryable PostgreSQL representation so applications can use consistent FastAPI endpoints instead of connecting directly to the database or calling TourData APIs themselves.

</Callout>

The database layer in `db.py` manages the PostgreSQL connection pool and individual connections. FastAPI routers use this layer to serve local data with pagination, read-only transactions, query timeouts, access policies, and domain-specific response models.

This separation gives consuming applications a stable API boundary. It also allows synchronization to continue independently of read traffic and lets the service expose derived data, including feedback aggregates, booking views, disposition data, alerts, and planning information.

## Nightly Azure Function

The timer-triggered Azure Function at `functions/nightly_sync/__init__.py` runs daily at 02:00 UTC. It resolves credentials and runs synchronization independently for each configured tenant.

For each tenant, the function:

- Resolves tenant-specific Web Trip and Dossier credentials.
- Opens the corresponding TourData clients.
- Synchronizes trips.
- Synchronizes bookings.
- Logs the result for that tenant.
- Skips tenants without the required credentials instead of aborting the entire run.

The function treats trip and booking synchronization independently because a tenant may have Dossier access without Web Trip access. The run fails visibly when no tenant successfully imports bookings, which prevents an apparently successful schedule from hiding a complete ingestion failure.

The same synchronization modules are also available through CLI commands such as `tdm-backfill`, `tdm-ingest`, and `tdm-enrich`. This keeps scheduled operations, manual backfills, and local maintenance workflows on the same ingestion implementation.
