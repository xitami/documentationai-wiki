## Integration landscape

TWG integrates with TourData APIs, Microsoft Entra ID, Azure infrastructure, LLM providers, and external webhook systems. These integrations form the upstream data pipeline, authentication layer, cloud infrastructure, and downstream notification channels.

## TourData APIs

TourData provides the source data that TWG mirrors into Azure PostgreSQL. Each API uses bearer-token authentication after login, with transport retries and retry-triggered re-login behavior.

  </Card>

  <Card title="Dossier API" href="#tourdata-apis" icon="database" horizontal="false">

  </Card>

  <Card title="Disposition API" href="#tourdata-apis" icon="settings" horizontal="false">

The Web Trip and Dossier APIs are separate upstream systems. Configure separate credentials for each API, even when both credentials belong to the same tenant.

Configured tenants include:

- `twr`
- `imb`
- `rmt`
- `voe`
- `exc`

<Callout kind="info">

TWG isolates credentials and source configuration per tenant. A failure in one tenant does not normally prevent other tenants from completing their synchronization runs.

</Callout>

The main upstream services are:

| API | Production service | Primary data |
| --- | --- | --- |
| Web Trip API | `ase-travelapi-prod.azurewebsites.net` | Trip catalogue and trip details |
| Dossier API | `ase-dossier-prod.azurewebsites.net` | Bookings, dossiers, surveys, questions, and choices |
| Disposition API | `ase-disposition-prod.azurewebsites.net` | Vehicles, staffing, dispositions, and transport planning |
| Address API | `ase-address-prod.azurewebsites.net` | Reisepersonal and customer addresses |

## Microsoft Entra ID

Microsoft Entra ID protects normal API routes with JWT validation and supplies the caller identity used for authorization decisions. The service also uses Entra ID for remote MCP authentication and mail sender authorization.

Configure the tenant and expected API audience with these settings:

<ParamField body="ENTRA_TENANT_ID" param-type="string" required="true" show-location="false">
  Microsoft Entra tenant identifier used to validate incoming tokens.
</ParamField>

<ParamField body="ENTRA_API_AUDIENCE" param-type="string" required="true" show-location="false">
  Expected audience value for API access tokens.
</ParamField>

Caller-policy groups apply authorization rules by integration purpose:

- `catalog`: Trip catalogue and related read access.
- `operations`: Operational and synchronization data.
- `feedback`: Surveys, ratings, and feedback enrichment.
- `aggregates`: Aggregate and read-model access.
- `platform`: Platform, administration, and integration operations.

Entra application claims, including the client ID or `azp` claim, identify the calling application. Mail permissions use application-specific sender authorization in addition to token validation.

<Callout kind="alert">

Production startup fails closed when `ENTRA_TENANT_ID` or `ENTRA_API_AUDIENCE` is missing. Configure both values before deploying the API or any protected integration.

</Callout>

## Azure infrastructure

TWG runs its ingestion, API, delivery, and deployment workloads on Azure. Terraform definitions for the infrastructure are stored under `infra/terraform/`.

| Azure service | Integration role |
| --- | --- |
| Azure Container Apps | Runs the API and scheduled jobs for synchronization, feedback ingestion, mail delivery, alert evaluation, and event fan-out. |
| Azure Functions | Runs the `nightly_sync` timer trigger at approximately 02:00 UTC. |
| Azure Database for PostgreSQL | Stores the multi-schema mirror and application data, including `tourdata`, `_sync`, `dispo`, `velo_log`, `kd_store`, `mail`, `alert`, `event`, and `feedback_analytics`. |
| Azure Key Vault | Stores secrets and supplies configuration through Key Vault references. Event endpoints store a `secret_ref` instead of the signing secret itself. |
| Azure Container Registry | Stores container images used by the API, jobs, and deployment workflows. |
| Azure Virtual Network | Provides network isolation and private connectivity to the database. |
| Log Analytics | Centralizes logs from Azure-hosted workloads. |
| Application Insights | Collects application telemetry and execution diagnostics. |
| Managed Identity | Lets Azure workloads access supported resources without storing credentials in application configuration. |
| GitHub Actions OIDC | Authenticates deployment workflows to Azure without long-lived deployment credentials. |

The nightly Function reads all configured tenants, obtains tenant-specific Web Trip and Dossier credentials, and synchronizes trips and bookings. Container Apps jobs handle independent workloads such as frequent imminent-trip synchronization, feedback ingestion, disposition ingestion, customer synchronization, and event delivery.

## Microsoft Graph and mail

TWG's production mail service uses Microsoft Graph with a Shared Mailbox. Sender access is controlled per application through the `mail.sender` and `mail.app_sender` records.

The mail flow is durable:

1. TWG renders and stores the complete message in the mail outbox.
2. A scheduled delivery job claims queued messages.
3. Microsoft Graph receives the delivery request.
4. The job records the attempt and retries eligible failures.
5. Retention processing redacts PII and later removes records according to the configured policy.

The mail service keeps message and attempt state separately. This allows operators to inspect delivery history without losing the original application-level message record.

## LLM providers

TWG uses OpenAI-compatible provider interfaces for feedback sentiment analysis, topic extraction, and trip recommendations.

OpenRouter is the default provider endpoint:

```text
https://openrouter.ai/api/v1
```

Anthropic is available through its OpenAI-compatible endpoint as a fallback:

```text
https://api.anthropic.com/v1/
```

Configure provider access and model selection with these settings:

<ParamField body="OPENROUTER_API_KEY" param-type="string" required="false" show-location="false">
  API key for the default OpenRouter provider.
</ParamField>

<ParamField body="ANTHROPIC_API_KEY" param-type="string" required="false" show-location="false">
  API key for the Anthropic provider.
</ParamField>

<ParamField body="ANTHROPIC_MODEL" param-type="string" required="false" show-location="false">
  Anthropic model used for general enrichment tasks.
</ParamField>

<ParamField body="ANTHROPIC_MODEL_SENTIMENT" param-type="string" required="false" show-location="false">
  Anthropic model used for sentiment analysis.
</ParamField>

The feedback pipeline stores provider-derived sentiment and topic results alongside survey analytics. Provider configuration belongs in deployment secrets rather than in source-controlled configuration.

## MCP and LLM clients

TWG exposes read-only access for LLM clients through several MCP deployment modes:

- **Local stdio server:** Runs locally for tools that launch the MCP process directly.
- **HTTP server:** Exposes MCP over HTTP for clients that connect to a running service.
- **Remote MCP deployment:** Provides a remotely hosted MCP endpoint with Entra ID authentication.

The available read-only tool domains include:

- Trips
- Bookings
- Feedback
- Aggregates
- Alerts
- Dispositions
- Notes
- Mail
- Reference data
- Schema metadata
- Directory and person data

Remote MCP clients authenticate through Microsoft Entra ID and are subject to the same caller-policy boundaries as other protected API consumers. MCP tools access the mirror through the API rather than writing directly to the database.

## Excellence webhook integration

TWG supports a dedicated `excellence-items` webhook format for Excellence integrations. The webhook sends changed trip codes as lightweight triggers:

```json
{
  "items": [
    {
      "type": "trip",
      "code": "TRIP-2048"
    }
  ]
}
```

The payload intentionally contains identifiers instead of a full trip record. Excellence uses each changed trip code to retrieve the complete trip state through its own integration path.

## BI direct database access

BI consumers can connect directly to the mirror PostgreSQL database when they need database-level access to source data or read models. Aggregate APIs and materialized views provide stable read models for dashboards, assistants, and operational reporting.

<Callout kind="info">

Use read-only database access for BI consumers. Keep application writes behind the TWG API or the owning application boundary so source mirror data and local operational state remain separated.

</Callout>

The database separates source-owned mirror data from application-owned data. Ingestion can refresh the `tourdata` schema without overwriting planning, Velo-Log, document, mail, alert, or event-delivery state.

## Velo-Log and kd-doc application boundaries

Velo-Log and kd-doc are external application consumers of TWG's API. Neither application connects directly to PostgreSQL.

- **Velo-Log:** Uses endpoints under `/api/v1/velo/*` and stores application-owned data in the `velo_log` schema.
- **kd-doc:** Uses endpoints under `/api/v1/kddoc/*` and stores document and workspace data in the `kd_store` schema.

Write access is independently gated:

<ParamField body="VELO_WRITE_ENABLED" param-type="boolean" required="false" show-location="false">
  Enables Velo-Log write operations when set according to the deployment configuration.
</ParamField>

<ParamField body="KD_DOC_WRITE_ENABLED" param-type="boolean" required="false" show-location="false">
  Enables kd-doc write operations when set according to the deployment configuration.
</ParamField>

This boundary prevents external applications from coupling their persistence logic to the mirror database schema. API consumers receive controlled access to the data and operations relevant to their application.
