## Welcome to TWG

The TWG platform mirrors master and operational data from TourData into Azure PostgreSQL and exposes it through an authenticated Read API with Microsoft Entra SSO. It powers nightly incremental sync, BI direct access, feedback analytics, disposition planning, customer document delivery, alerting, and event-driven webhooks, all behind a multi-tenant architecture serving the Twerenbold, Imbach, RMT, Vögele, and Excellence brands.

## Architecture at a Glance

The platform runs on Azure with private-by-default infrastructure: PostgreSQL Flex integrated into a VNet, Container Apps for the Read API and sync jobs, Key Vault for secrets, and Application Insights for observability. Data is ingested from four TourData upstream APIs: Web Trip, Dossier, Disposition v2, and Address, and stored in domain-specific PostgreSQL schemas.

<Callout kind="info" collapsed="false">
  Source-owned data in the `tourdata` schema is refreshed by ingestion and remains read-only. Application-owned schemas, including `dispo`, `velo_log`, `kd_store`, `mail`, `alert`, and `event`, support writes through their respective API boundaries, gated by feature flags.
</Callout>

## Multi-Tenant

Each brand is a separate tenant with isolated credentials, sync runs, and domain data. Tenants include `twr` (Twerenbold), `imb` (Imbach), `rmt` (RMT), `voe` (Vögele), and `exc` (Excellence). A trip is identified by `(tenant_id, trip_code)`, so the same trip code can exist across tenants without collision.

## Environments

The platform has two environments: `dev` and `prod`. There is no `test` environment. Infrastructure defaults differ materially between them: replica counts, mail gates, event transport, alert sender, and model settings. See the [configuration page](tourdata-mirror/configuration) for the full variable reference.

<Callout kind="tip" collapsed="false">
  Always validate migrations and sync changes against `dev` before tagging a production release. TourData Mirror has no test environment.
</Callout>
